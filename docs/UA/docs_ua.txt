====================================== ДОКУМЕНТАЦІЯ КАЛЬКУЛЯТОРА GEAREO ======================================


-------------------------------------- 0. Комплект документації --------------------------------------

0.1. Призначення

Це пояснювальна частина комплекту для відтворення фізичного 10-значного калькулятора Geareo: архітектура, взаємодія підсистем, причини нетривіальних рішень, порядок виконання й специфіка середовища.

Комплект містить 72 Circuit: 43 функції та 29 модулів. Первинні визначення не дублюються:
- functions_FINAL.txt — реалізація окремих функцій, входи, виходи, таймінги, формули;
- modules_FINAL.txt — фізичні Circuit, їхні порти, внутрішні з'єднання та алгоритми;
- contracts_FINAL.txt — нормативні коди, формати, таблиці поведінки, обмеження й протоколи;
- docs_FINAL.txt — принципи, система як ціле, причини рішень і порядок відновлення.

0.2. Посилання

D§6.3 — розділ цього документа; C§21 — розділ контрактів; M:SyncBuffer — модуль; F:funFlowDecoder — функція. Наприклад: коди Flow — C§7, повна матриця переходів — C§21, декодер — F:funFlowDecoder, вузол фіксації — M:FlowController.

У посиланнях M: та F: використовується точна назва Circuit, не номер рядка. C§ вказує на номер розділу фінальних контрактів. Вкладений список, конкретна формула чи розводка — у відповідному M/F, а не в docs.

0.3. Терміни перед читанням

Circuit — фізична схема Geareo; M: — модульна схема, F: — функція. Scalar — один числовий сигнал. Bus (скорочено B) — шина з кількох впорядкованих слотів: B4 має чотири, B11 — одинадцять; B без числа означає generic bus, ширину якої задає екземпляр. Слот нумерується з 0. Назви фізичних портів — C§1.

Native number — одне числове значення рушія Geareo; chunk — окрема частина десяткової мантиси. Entry — буквальний запис користувача; Number — нормалізоване математичне значення. Frame — готові значення та крапки для десяти позицій дисплея.

Command — захоплена дія кнопки; Mode — стан інтерфейсу ENTRY/RESULT/ERROR; Flow — одноразово визначений маршрут виконання команди. Worker — контролер, який виконує свою групу команд. Candidate — новий стан у підготовці; Current — чинний стан, доступний читачам. Valid — дозвіл довіряти пакету; Release — підтвердження завершення його обробки. Тік — одна одиниця логічного часу симуляції.

Ці поняття докладно розкрито нижче; точні значення, структури й протоколи — у contracts_FINAL.txt.


-------------------------------------- 1. Призначення проєкту --------------------------------------

1.1. Що отримує користувач

Електронний калькулятор із 10 позиціями дисплея та 23 кнопками: цифри 0–9, +, −, ×, ÷, десяткова крапка, зміна знака, видалення останнього символу, =, C, M+, M−, MR, MC. Є ланцюгові обчислення, повторний = і робота з окремою пам'яттю M.

У режимі введення дисплей зберігає буквальний вигляд числа, включно з крапкою й введеними кінцевими нулями. Після обчислення показ автоматично обирає звичайний FIXED або запис через E (SCIENTIFIC); перемикача формату для користувача немає. Визначення обох форматів — D§13.3.

1.2. Числові та фізичні характеристики

Внутрішній результат має до 10 значущих десяткових цифр; Exp для успішного арифметичного Number: −999999…999999. Це межа внутрішнього числа, а не обіцянка показати будь-яке таке число на десяти Digit. Для відображення значення може бути додатково округлене без зміни збереженого Number; якщо воно не вміщається, виводиться ErrOr. C§8, C§28, C§39–40.

Знак може займати окрему позицію. Крапка прив'язана до Digit й окремого місця не займає. Фізичний індикатор M показує, що збережена пам'ять ненульова; індикатора помилок як окремого світлодіода немає. Помилки — це напис ErrOr на основному дисплеї, режим ERROR і скидання через C. M:ErrorRenderer, M:Indicator.

1.3. Поведінка та обмеження для користувача

Натискання обробляються послідовно: у калькулятора немає черги швидких натискань. Занадто коротку кнопку можна втратити до захоплення; під час виконання захопленої команди нові короткі натискання ігноруються. Одночасно натискати кілька кнопок не передбачено. Арифметична помилка, ділення на нуль або неможливість показати результат переводить інтерфейс у ERROR; C очищує обчислення й введення, але не M. MC очищує лише M. C§21, C§29–30.

1.4. Архітектурна межа

Жоден renderer не змінює математичний стан. Жодна фізична кнопка не запускає ALU без транзакційного керування. Кожний state bank має єдиного штатного власника запису; наступний пакет не виконується до завершення поточної транзакції.


-------------------------------------- 2. Фізичний калькулятор --------------------------------------

2.1. Scene та кнопки

На сцені: 23 активні кнопки, 10 однакових Digit і окремий Indicator для M. Кожна Digit отримує Value (код символу) і Dot (крапку); позиції нумеруються 0–9 зліва направо. Indicator не займає місця Digit. Порядок кнопкових шин — C§14.

Сітка 5×5 кнопок:

| MC  | MR  | M+  | M−  |  ÷  |
|     |  7  |  8  |  9  |  ×  |
|     |  4  |  5  |  6  |  −  |
| BSP |  1  |  2  |  3  |  +  |
|  C  | +/- |  0  |  .  |  =  |

Два порожні місця не є командами.

2.2. Дія кожної групи

0–9 → Digit (301), параметр Value = натиснута цифра; +/−/×/÷ → Operation (302), параметр 201/202/203/204. Крапка → Dot (303), = → Equals (304), C → Clear (305), +/- → ToggleSign (306), BSP → Backspace (307). M+ → 308, M− → 309, MR → 310, MC → 311. Інші команди не передбачені. Коди й payload — C§5, C§13; фізичні входи — M:MainController.

2.3. MainController

M:MainController — кореневий Circuit та центральна точка підключення сцени. Він передає сигнали кнопок у M:InputController; зв'язує керування, workers, стани й renderers; видає десять пар value/dot та indicator. Семантика команд не обчислюється в самому кореневому з'єднанні.

2.4. Межа scene / logic

Через фізичну межу проходять кнопкові рівні та виходи символів/точок. Результати власної арифметики й потенційно від'ємні проміжні значення залишаються всередині Circuit. Повну topology fan-out див. M:MainController.


-------------------------------------- 3. Основні представлення даних --------------------------------------

3.1. Entry

Буквальний запис користувача, а не готове число для ALU. Зберігає введені цифри, їхню кількість, знак та положення крапки; тому може відрізняти 0, -0, 0.0, 0.00. Фізично EntryState використовує B6, назовні має шість логічних полів. C§10–11.

3.2. Number: навіщо свій формат

За фізичними спостереженнями нативне число Geareo надійно утримує приблизно сім значущих десяткових цифр. Одне native-значення не годиться для повної десятизначної мантиси: молодші цифри губилися б. Тому Number — шина B4 [Hi,Lo,Exp,Neg]: два окремі п'ятизначні chunks, десятковий показник і біт знака. Exp визначає положення першої значущої цифри; крапка як поле Number не зберігається.

Математичне значення = (−1)^Neg × (Hi × 100000 + Lo) × 10^(Exp−9).

Приклад: 0.0012345 → Hi=12345, Lo=0, Exp=−3, Neg=0. У ненульового Number Hi нормалізований; нуль завжди [0,0,0,0], без мінуса. Множення Hi×100000 у формулі — тільки математичний опис: фізично Hi та Lo ніколи не з'єднуються в єдиний native scalar. C§8.

Оскільки в ненульового канонічного Number Hi завжди ≥10000, для перевірки нуля достатньо Hi==0. Це використовується в арифметичних функціях, зокрема funMagnitudeOrder, та для індикатора пам'яті M.

3.3. Entry → Number

F:funEntryToNum перетворює позиційний буквальний запис на нормалізований Number, прибираючи різницю між літеральними нулями та математичним нулем. Це використовується під час арифметичних команд і M+/M− у ENTRY. Відображення введення працює без цього перетворення: M:EntryRenderer читає буквальні поля.

3.4. Command, Mode, Flow, Frame

Command B2 — Code та Value; кнопка задає намір, але не вирішує, як його виконати. Mode — поточний контекст інтерфейсу: ENTRY (введення), RESULT (результат), ERROR (помилка). Flow — рішення за Command і старим Mode: PASS, DROP, BEGIN_ENTRY, TO_RESULT або CLEAR. Це не чотири різні типи пам'яті, а різні ролі. Frame — дві B10 шини символів і крапок для показу. C§6–7, C§12–14, C§21–22.

3.5. Persistent state

Стан відокремлений від комбінаційних функцій: EntryState; ArithmeticState (Result, Operand, Operation, OpPending, RhsReady); MemoryState M; semantic Mode. Усі state banks видають публічні дані з Current, не з Candidate. C§15–20.


-------------------------------------- 4. Загальна архітектура --------------------------------------

4.1. Data path

Buttons → CommandEncoder/SyncBuffer → Command B2 → worker → Candidate → Current → ResultNumberSelector/renderers → DisplayController → Digit.

Паралельно: EntryCurrent → EntryRenderer і F:funEntryToNum; ArithmeticCurrent → CalculationController/ResultNumberSelector; MCurrent → MemoryController/CalculationController/Indicator.

4.2. Control path

Input.Valid → StateController → FlowController → PreparationController → MainValid → один worker → WorkerRelease → POST → Mode commit → GlobalRelease. Кореневий Valid утримує транзакцію, хоча worker уже може завершити роботу. C§34–36.

4.3. Stateful та stateless

Stateless (комбінаційні) вузли обчислюють вихід із теперішніх входів: F-функції, ArithmeticUnit, CommandEncoder, renderers, selector, gating. Stateful-вузли мають власну історію: Memory/BusMemory, EntryState/CalculatorState, SyncBuffer, SRFlag, synchronizers і feedback-таймер. Тому вхід кнопки не дорівнює вже завершеній команді, а кандидатний результат не дорівнює поточному стану. Stateful-вузол не можна підміняти просто формулою.

4.4. Основні ролі

M:InputController — захоплення B2. M:StateController — порядок фаз і Mode. M:EntryController — буквальні команди. M:CalculationController — Operation/Equals/MR. M:MemoryController — M+/M−/MC. M:CalculatorState — збереження Mode/Arithmetic/M. M:DisplayController — остаточний вибір кадру. Точний wiring — M:MainController, ownership — C§18–19.


-------------------------------------- 5. Система вводу --------------------------------------

5.1. Encoder

M:CommandEncoder отримує чотири шини кнопок, формує один Command B2 і Capture=OR усіх 23 кнопок. Кожна кнопка відкриває власну гілку B2 через BusGate; гілки з'єднуються фізичним дротом. Encoder не вирішує semantic Mode і не гарантує пріоритету одночасних кнопок. C§5, C§13–14.

5.2. Command mailbox

M:InputController подає raw Command і Capture до M:SyncBuffer. Споживач може читати пакет тільки після Valid=1. До цього combinational Command і пам'ять можуть ще змінюватися; Valid відділяє захоплений пакет від поточного стану кнопок.

5.3. Захоплення та обмеження кнопок

Між фізичним натисканням і Valid є затримка поширення: дуже короткий імпульс може згаснути до захоплення, тож команда загубиться. Якщо пакет уже захоплено, його B2 зберігається аж до GlobalRelease, а короткі натискання, що повністю припали на зайнятий інтервал, не потрапляють у чергу — її немає.

Утримана кнопка не має автоматично повторюватися: Used блокує повторне захоплення до відпускання Capture і rearm. Якщо одночасно активні кілька кнопок, CommandEncoder не вибирає одну з них випадково чи за пріоритетом: злиття гілок може утворити конфліктний пакет. Штатне правило — натискати по одній кнопці.

5.4. Поділ відповідальності

Encoder кодує рівні; SyncBuffer гарантує стабільний пакет; StateController визначає порядок виконання; workers інтерпретують команду. Змішування цих ролей повернуло б проблему повторного запуску й неусталених даних.


-------------------------------------- 6. Система синхронізації --------------------------------------

6.1. Для чого потрібні протоколи

Дроти, з'єднання та порти передають значення миттєво, без додаткових тіків. Затримку створюють обчислювальні примітиви: кожен послідовний примітив додає один логічний тік.

Через ці затримки різні шляхи однієї схеми можуть оновлюватися неодночасно. Дані можуть ще змінюватися, коли сигнал керування вже активний. Тому потрібно окремо визначати, коли пакет захоплено, коли його виходи стабільні та коли завершено обробку.

Використовуються два протоколи:
- Передавання пакета: Ready → Capture → Valid → Release.
- Виконання фази: Valid + Execute → Work → Done → Release.

Перший забезпечує стабільність переданих даних, другий керує часом виконання. Candidate/Current додатково розділяє обчислення нового стану та його commit. C§20, C§31–33.

6.2. SyncBuffer: фіксація й підтвердження пакета

M:BusMemory зберігає пакет у feedback-контурі, проте після закриття Write його нове значення ще рухається через внутрішні BusGate. Якщо одразу підняти Valid, споживач може зчитати попередню або перехідну шину. Тому Accept спершу встановлює Lock і закриває Write; шлях NOT(write) → M:Diode → M:Diode затримує ознаку Settled. Valid з'являється лише за Lock AND Settled, коли вихід уже можна читати.

Lock означає «цей слот зайнятий», Used — «ця активність Capture уже використана». Release знімає Lock, але нового Ready немає, поки Capture/Release/Settled не спали й Used не очистився. Так одне довге натискання не породжує серію команд. SyncBuffer має місткість один пакет, не FIFO. Формули — M:SyncBuffer, M:SRFlag.

6.3. FeedbackSynchronizer: чому Done не є Release

M:FeedbackSynchronizer починає Work лише коли RootValid і Execute дозволяють цю фазу. Timer після Delay видає Done на один тік — це зручна локальна подія для завершення Work або семплювання помилки. Але наступна фаза може перевірити сигнал пізніше й пропустити цей імпульс. Тому Release запам'ятовується як рівень до спаду Valid. Done означає «подія відбулася», Release — «завершення доступне іншим вузлам».

Один worker запускається тільки власною командою; чужу транзакцію він не має права звільнити. ComputeSynchronizer запускає commit-фазу; WorkerRelease виникає лише після CommitSynchronizer. GlobalRelease належить StateController. C§32–36.

6.4. ExecTimer

M:ExecTimer запускається фронтом Start, відраховує задані логічні тіки, видає один Done. Delay не менше 5. Його feedback-лічильник після завершення може переходити 0↔−1; подія Done перевіряє значення 5, тому цей idle-цикл її не відтворює. Опис із t у модулі — модель фізичної петлі, не окремий rising-edge Circuit. Утриманий Start не запускає таймер знову.

6.5. State update як третя межа

У worker Compute сигнал Work відкриває Candidate, Current закритий. Коли Work падає, Candidate заморожено, Current відкривається для commit. Окремий CommitSynchronizer чекає час поширення до видачі worker Release. Значення з Candidate не використовують як публічний стан до цього моменту. C§20, C§41–43.

6.6. Повторне використання

SyncBuffer працює з generic bus і не знає значення його слотів; FeedbackSynchronizer не знає операції worker. Тому обидва можна застосовувати поза калькулятором, якщо producer витримує правила payload/Capture, а consumer — Valid/Release та безпечні Delay.


-------------------------------------- 7. Транзакційна модель --------------------------------------

7.1. Один пакет — одна транзакція

Кожне прийняте натискання породжує один заморожений Command. Semantic Mode береться зі старого авторитетного ModeCurrent. F:funFlowDecoder визначає Flow за старим Mode та Code, M:FlowController фіксує цей Flow після DecodeDelay. Зміна Mode наприкінці транзакції не може повторно декодувати вже захоплену команду. C§21, C§34.

7.2. Порядок фаз

Input Capture → Decode → Frozen Flow → PRE → (Worker Compute → Commit або skip) → POST-check → Mode commit → GlobalRelease.

PRE працює для кожного Flow, навіть без reset. Тільки після його Ready вмикається MainValid нормального worker. Один normal worker на команду; для DROP та CLEAR normal worker немає. Таблиці — C§19, C§22, C§35.

7.3. PRE

M:PreparationController виконує EntryReset перед BEGIN_ENTRY; EntryReset та ArithmeticReset перед CLEAR; у решті випадків очікує те саме безпечне вікно. Reset є завершеним до запуску normal worker. CLEAR використовує PRE й потім POST, але не виконує EntryController як окрему команду.

7.4. Worker, Compute та Commit

Worker — спеціалізований виконавець частини CommandCode, який читає Current, обчислює Candidate, керує Work і повідомляє про завершення. Entry, Calculation, Memory — три normal workers. Їхні ComputeDelay різняться; worker Release виникає після commit, а не при raw-обчисленні. Взаємовиключність команд захищає банки від конкуруючого normal write.

7.5. POST, Mode і завершення

M:StateController чекає WorkerRelease (або PreReady для DROP/CLEAR), перевіряє утриману помилку та ResultFits, формує TargetMode. Помилка має пріоритет над нормальним переходом. Запис Mode йде через ModeCandidate → ModeCurrent у власному часовому вікні. Тільки після його завершення GlobalRelease знімає Input/Flow пакети та дозволяє нове захоплення.

7.6. Переходи

500 PASS — виконати команду без зміни Mode; 501 DROP — не виконувати; 502 BEGIN_ENTRY — спочатку очистити Entry, потім виконати його команду і перейти в ENTRY; 503 TO_RESULT — виконати й перейти в RESULT; 504 CLEAR — очистити Entry/Arithmetic і перейти в ENTRY, M не зачепити. Повна матриця режимів і команд — C§21–22.


-------------------------------------- 8. Модель стану --------------------------------------

8.1. Mode і місце зберігання

Semantic Mode: ENTRY/RESULT/ERROR. Рівно одне фізичне M:CalculatorState містить Mode, ArithmeticState B11 та M B4. EntryState — окремий підмодуль M:EntryController. Контролери не є сховищами поточного арифметичного значення. C§15–20.

8.2. Чому дві комірки

Пам'ять Geareo — це Valve/BusGate із замкненим фізичним feedback, а не миттєвий регістр. Якщо новий стан одразу записувати до тієї комірки, з якої обчислюється наступний стан, її ще неусталений вихід повертається в обчислення. У тестах Mode це давало проміжні невалідні коди. Перша комірка Candidate приймає next state під час Work; друга Current тим часом ізольована й лишається джерелом старого стану. На Work↓ Candidate закривається, Current приймає вже підготовлений результат. Це розриває небезпечний read-modify-write feedback.

8.3. Чому критичні тіки

Memory не миттєвий регістр: Valve/BusGate і feedback поширюють значення через кілька тіків. Work↓ лише відкриває копіювання, не засвідчує, що Current вже правильний. Без окремого commit-вікна наступний worker міг би прочитати перехідний стан. Особливо важливо зберегти реальні Pass/NOT на керуванні Write Mode й M, а не заміняти їх абстрактними NOT/NOT: різниця шляхів руйнувала розділення фаз. M:CalculatorState.

8.4. Авторитетність і атомарність

ArithmeticState записується одним B11-пакетом, а не частинами Result/Operand/flags; MemoryState — одним B4. Публічні виходи походять з Current. ModeCurrent використовується також для наступного decode. Normal writer: EntryController для Entry; CalculationController для Arithmetic; MemoryController для M; StateController для Mode. C§18–20.

8.5. Reset override

Reset не стає другим normal worker. PreparationController окремо керує reset-проходом потрібного банку. EntryState при Reset примусово передає явну нульову B6 й відкриває обидві пам'яті, навіть при Work=1; Arithmetic reset подає повний DefaultArithmetic і дозвіл запису Candidate, без дострокового відкриття Current під активним арифметичним Work. C§11, C§17, C§30.


-------------------------------------- 9. Система Entry --------------------------------------

9.1. Буквальна семантика

Entry зберігає буквальний запис користувача: знак, позицію крапки та кількість уведених цифр. Тому 1, 1.0 і 1.00 мають різний Entry, хоча відповідають одному математичному Number. Додаткові початкові нулі без крапки не накопичуються. C§10.

9.2. Чому LenRaw=Len−1

Фізичний B6 має починатися з усіх нулів, але логічне Entry за умовчанням має одну цифру 0 (Len=1). Тому всередині зберігається LenRaw=Len−1, назовні відновлюється Len=LenRaw+1. Це узгоджує порожню фізичну пам'ять, Clear і перший показ дисплея, без спеціального InitBusMemory для EntryState. M:EntryState, C§11.

9.3. Команди буквального вводу

Digit додає цифру, доки є вільна позиція; Dot ставить точку після поточної останньої цифри, повторна Dot нічого не змінює; ToggleSign додає знак тільки за доступної позиції; Backspace забирає кінцеву крапку або цифру, зберігаючи щонайменше один 0 та поточний знак. Крапка передається незалежним Dot і не займає Digit. Точні умови — C§10; реалізація — M:EntryController.

9.4. Відображення та перехід до арифметики

M:EntryRenderer малює Entry без нормалізації, через F:funEntryCell. Коли потрібне математичне значення, F:funEntryToNum формує Number B4. Нове введення після RESULT спочатку проходить Flow 502 і EntryReset: старий результат не стирається в ArithmeticState просто через натиснуту цифру.


-------------------------------------- 10. Модель обчислень --------------------------------------

10.1. Навіщо Result та Operand

Result — накопичений результат/лівий аргумент; Operand — окреме збережене праве число. Operation зберігає код операції. Після Equals Operand повинен пережити завершення pending-операції для повторного Equals. Це не можна надійно відновити з одного лише Result. C§15, C§23–24.

10.2. Чим різняться OpPending і RhsReady

OpPending=1 означає, що є незавершена операція з Result як лівим аргументом. RhsReady=1 означає, що Operand містить новий правий аргумент, готовий для використання, але ще не застосований. Вони незалежні за призначенням: pending operation може існувати без нового RHS; старий Operand може зберігатися для повтору, не будучи новим RHS. Публічний ResultNumberSelector обирає Result або Operand за RhsReady, а не за OpPending. C§15, C§27.

10.3. Operation

У ENTRY без pending нове Entry стає Result і Operand, виставляється нова Operation. У ENTRY з pending спочатку застосовується попередня операція до Entry, потім зберігається нова Operation: chaining. У RESULT без pending починається нова операція від Result; за pending без готового RHS повторне натискання оператора може лише замінити Operation; із готовим RHS попередню операцію спершу завершують. C§23.

10.4. Equals

Якщо pending немає й користувач перебуває в ENTRY, Equals приймає Entry як Result без арифметики. Якщо pending є в ENTRY, Entry — RHS. У RESULT використовується збережений Operand; це дає implicit RHS та repeated Equals. Після успішного обчислення OpPending скидається, але код Operation і Operand можуть лишатися для повторного Equals. Якщо Operation=None і pending немає, це no-op. C§24.

10.5. MR у арифметичному ланцюжку

MR виконує CalculationController, бо змінює ArithmeticState, а не M. Якщо pending немає, M стає поточним Result і Operand. Якщо pending є, M потрапляє в Operand, RhsReady=1; обчислення відкладене до наступної операції чи Equals. C§25.

10.6. Захист результату

Лише гілки, яким потрібна арифметика, виставляють UseALU. Неактивна ArithmeticUnit може обчислити invalid operation, але її raw error не є помилкою команди. Реальна raw ALU помилка підмінює наступний B11 старим Current; sticky Error зберігає факт збою для POST. M:CalculationController, C§29, C§40.


-------------------------------------- 11. Система пам'яті M --------------------------------------

11.1. Незалежність від ArithmeticState

M — окремий канонічний Number B4 із власними Candidate/Current. M зберігається при Clear. Пам'ять читають CalculationController для MR і MemoryController для M+/M−; записує тільки MemoryController. Індикатор M читає старший chunk канонічного MCurrent: за нормалізованого ненульового Number Hi завжди ненульовий. C§16, C§18–19.

11.2. Яке число береться для M+/M−

У ENTRY це перетворене EntryNumber; у RESULT — Result або Operand за RhsReady. Отже, пам'ять працює з математично актуальним числом, а не з текстом на дисплеї та не з довільним полем B11. C§26–27.

11.3. M+, M−, MC, MR

M+ додає поточне число до M; M− віднімає; MC записує канонічний нуль без ALU. Для M+/M− у M:MemoryController є власна ArithmeticUnit; вона не розділяється з CalculationController. MR M не змінює і належить CalculationController. Clear не еквівалентний MC. C§25–26, C§30.

11.4. Збій

При активній арифметичній помилці M-кандидат підмінюється старим MCurrent, а sticky memory error передається в POST. MC не використовує ALU, тому не залежить від raw error неактивної гілки. Для MemoryController Compute=47, Commit=5; для CalculationController commit окремо 20. C§29, C§43.


-------------------------------------- 12. Арифметична модель --------------------------------------

12.1. Чому своя арифметика, а не native + / × / ÷

Навіть якщо зберегти правильні Hi та Lo, одна native-операція над їхньою об'єднаною десятизначною мантисою могла б знову загубити молодші цифри. Тому всі чотири операції будуються з арифметики менших chunks із перенесеннями, вирівнюванням і окремою нормалізацією. Для Add/Sub недостатньо просто додати Hi до Hi та Lo до Lo: різні Exp треба вирівняти, врахувати знак, переноси й запас цифр для округлення. Тому використовується B5 із п'яти chunks (25 десяткових розрядів). Це робочий простір, не формат збереженого результату. C§8–9, F:funAddSub.

12.2. Number і нормалізація

Ненульова мантиса має десять значущих цифр, старший Hi починається ненульовою цифрою. Exp задає десяткову позицію, Neg — знак. Нуль один: [0,0,0,0]. Результат після арифметики повертається в канонічний Number; Exp успішної операції обмежений ±999999. C§8, C§38, C§40.

12.3. Add/Sub

F:funMagnitudeOrder визначає більший модуль; F:funShift25 вирівнює числа у B5 з запасом для переносу й округлення; F:funWideAdd25/F:funWideSub25 працюють із беззнаковими chunks. Для віднімання меншого з більшого дотримується A≥B; знак формує F:funAddSub. F:funNormalizeAddSub25 повертає канонічну мантису та Exp. Детальні зсуви й guard — C§9, F:funAddSub.

12.4. Mul

F:funMulCore збирає добуток із часткових 5×5-розрядних добутків, F:funMulNormalize10 нормалізує десятизначний результат та коригує Exp. Великої нативної мантиси немає. Арифметичне округлення виконується до збереження Number. F:funMul, F:funMul5x5.

12.5. Div

F:funDivInit готує дільник і виявляє ділення на нуль. F:funDivCore використовує шість послідовних двоцифрових quotient-кроків; перші п'ять пар утворюють 10 цифр, остання служить guard для округлення. Оцінка частки та корекція залишку розділені між F:funDivQHat, F:funDivMulD, F:funDivCorrectR, F:funDivPairStep. Передумови допоміжних функцій — C§38, не замінювати їх довільним прямим викликом.

12.6. Rounding і помилки

Арифметичне округлення визначає збережений десятизначний Number; помилка ділення на нуль або вихід Exp за допустимий діапазон не commit-иться. Display rounding — наступний незалежний крок для фізичних десяти позицій; він не змінює Result, Operand чи M. Half-up реалізовано F:funRound, не native round. C§39–40.


-------------------------------------- 13. Система відображення --------------------------------------

13.1. Єдиний Frame

Усі renderers виробляють дві B10 шини Values і Dots. Value — цифра або спеціальний символ; Dot — окремий біт відповідної позиції. Схема M:DisplayController не обчислює цифри, а вибирає цілісний Frame. C§3, C§12, C§28.

13.2. Три джерела кадру

M:EntryRenderer виводить буквальні цифри за Len/Neg/DotOn/DotAfter. M:ResultRenderer показує математичний Number із ResultNumberSelector. M:ErrorRenderer формує постійний напис ErrOr без окремого error-індикатора. Значення та крапки від різних renderer не змішуються.

13.3. Що означають FIXED і SCIENTIFIC

FIXED — звичайний десятковий запис числа без букви E, наприклад 123.45 або 0.0012. SCIENTIFIC — науковий запис через E, тобто мантиса × 10 у степені показника; умовно 1.2345E6 означає 1.2345 × 10^6. E займає позицію Digit, як і знак показника, якщо він від'ємний. Це не дві різні математичні величини, а два способи показати той самий Number. Режим обирається автоматично за Exp, знаком і місткістю дисплея.

M:ResultRenderer паралельно готує обидва Frame; F:funDisplayMode обирає формат. У FIXED кількість цифр обмежують F:funPrecision/F:funRoundNumber/F:funTrimZeros. У SCIENTIFIC потрібно додатково помістити E та цифри Exp; F:funScientificRound повторно перевіряє місткість після округлення, яке могло збільшити Exp. Якщо навіть SCIENTIFIC не вміщається, Fits=0 і показується ErrOr. Збережений Number не змінюється. C§28, C§39; клітинки — F:funFixedCell, F:funScientificCell.

13.4. Вибір та ERROR

ENTRY показує Entry; RESULT показує Result, якщо Fits=1, і Error Frame, якщо Fits=0; ERROR завжди показує Error Frame. Невідомий Mode теж переводить відображення у Error Frame. ResultFits також іде до StateController: POST може записати ERROR Mode. C§28–29.

13.5. Публічні цифри та індикатор

M:MainController розводить Values[i]/Dots[i] на Digit[i] для i=0..9. Indicator показує наявність ненульового M. Індикатор не залежить від renderer і не займає Value/Dot слот. M:Digit, M:Indicator.


-------------------------------------- 14. Модель часу --------------------------------------

14.1. Логічний тік

Один фізичний обчислювальний примітив (Valve, Pass, NOT, AND, OR тощо) має затримку рівно один логічний тік. Послідовні стадії додаються, паралельні завершуються за найдовшим шляхом. Wire, junction, Via, Port і оболонка custom Circuit не додають власного тіка. TPS змінює секунди, але не логічний порядок. C§41.

14.2. П'ять різних вимірів

Не плутати: затримка одного елемента; критичний шлях F-функції; ComputeDelay для worker; CommitDelay після Work↓; повна тривалість натискання → завершення транзакції. До повного часу додаються захоплення пакета, Decode, PRE, POST, Mode commit і поширення сигналів між стадіями. C§41–43.

14.3. Обчислення

Підтверджені арифметичні критичні шляхи: Add/Sub=44, Mul=28, Div=176 тіків; M:ArithmeticUnit додає 3 на вихідний вибір. Відповідні ALU ComputeDelay: 47, 47, 31, 179. EntryController використовує консервативні 20, CalculationController без ALU — 20, MemoryController усіх команд — 47. Повні значення допоміжних F-функцій — C§42.

14.4. Фази та commit

Decode, PRE, POST-check, ModeCommit — окремі вікна по 20; CalculationController Commit=20; MemoryController Commit=5, це мінімально допустима затримка ExecTimer. Work↓ не дорівнює WorkerRelease. Значення Current вважається готовим для наступної команди тільки після завершеного commit і глобального циклу. C§35, C§43.

14.5. Точність часових тверджень

Тіки внутрішніх примітивів детерміновані; не додавати вигаданих latency для F-функцій без окремого виміру. Дані про фізичну scene/world-взаємодію не прирівнювати автоматично до внутрішніх single-tick гарантій. Невиміряні combinational шляхи покриваються затвердженими робочими вікнами або новими вимірами.


-------------------------------------- 15. Startup і reset --------------------------------------

15.1. Самоініціалізація

M:InitMemory та M:InitBusMemory мають одноразовий фізичний init-шлях. На fresh startup константа 1 та затриманий NOT(1) коротко утворюють одночасні одиниці; AND(1,NOT(1)) дає короткий імпульс, що відкриває InitGate. Це не булева тотожність усталених сигналів, а перехідний процес поширення. Після імпульсу нормальний feedback зберігає дані, InitValue/InitBus більше не переписують стан.

15.2. Що саме ініціалізується

ModeCandidate — 401 через InitMemory, ModeCurrent підхоплює значення у спокої. ArithmeticCandidate — повний B11 DefaultArithmetic через InitBusMemory, включно з Operation=200; ArithmeticCurrent копіює його. EntryState B6 і M B4 стартують із фізичних нулів; Entry LenRaw=0 означає логічний Len=1. C§17, C§37.

15.3. Перша команда

Окремого InitializationController або InitReady немає. RootValid походить від InputController; startup-дані мають усталитися до завершення DecodeDelay=20. Не перетворювати одноразовий startup на runtime reset кожної транзакції.

15.4. Runtime reset

Flow 502 очищує Entry перед новим введенням. Flow 504/Clear очищує Entry та ArithmeticState і встановлює Mode ENTRY у POST, але не змінює M. MC очищує тільки M. Entry reset пише явну нульову B6, а не «відсутність сигналу»; Arithmetic reset пише весь DefaultArithmetic з Operation=200. C§30.


-------------------------------------- 16. Специфіка Geareo та фізичних Circuit --------------------------------------

16.1. Точність native number

У Geareo спостерігалася надійна нативна точність приблизно 7 значущих десяткових цифр. Тому десятизначну мантису Number збережено в окремих Hi/Lo, а 25-значний робочий B5 розділено на п'ять chunks. Об'єднання цих частин в один native scalar призвело б до втрати молодших значущих цифр. D§3.2, D§12.1.

16.2. Native round

Спостерігалося round-to-even: 1.5→2, 2.5→2. Проєкт вимагає half-up для невід'ємної мантиси, тому використовує F:funRound = floor(x+0.5). Арифметичне й дисплейне округлення — два різні кроки. D§12.6.

16.3. Від'ємні значення через scene

У фізичних тестах від'ємні значення на зовнішніх circuit/scene connections могли перетворюватися на 0; усередині вкладеної логіки вони працювали. Тому математичні й потенційно від'ємні проміжні сигнали залишаються в M:MainController, а назовні виходять додатні коди символів і Dot. Це спостереження старих тестів, не гарантія для кожного connection Geareo.

16.4. Startup transient

Константи та входи після запуску не стають усталеними одночасно. Саме цей короткий перехід дає імпульс AND(1,NOT(1)) у M:InitMemory/M:InitBusMemory. Зворотний бік: інші порівняння на startup теж можуть тимчасово видати хибні значення. До завершення початкового settle не трактувати проміжні коди як штатний стан. D§15.

16.5. Memory, Pass та затримка feedback

M:Memory використовує WriteValve → feedback Valve → вихідний Pass. Pass ізолює замкнений контур від зовнішньої лінії. M:BusMemory повторює цей ланцюг через покомпонентні BusGate; Init-варіанти додають одноразовий шлях ініціалізації. При Write↓ зворотний контур ще поширює останні дані: окремий таймінг/settle потрібен до авторитетного читання. D§6, D§8.

16.6. Шини: Valve та BusGate

M:BusGate відкриває окремий Valve для кожного слоту (до B15). При передачі двослотової Command B2 через простий scalar Valve у розробці спостерігали зависання другого слоту; заміна на покомпонентний BusGate виправила проблему. В окремому простому тесті ефект не повторився, тому це проєктне спостереження, а не універсальна властивість Valve. M:CommandEncoder, M:BusGate.

16.7. Об'єднання фізичних дротів

wire(a,b,...) у M — спільний фізичний провід, не OR і не арифметичне додавання. Gated-гілки можна зводити разом, лише коли джерела взаємно виключені. Кілька одночасно активних джерел можуть чергуватися між тіками чи конфліктувати; це вже проявлялося на Capture в CommandEncoder. Для логічного OR потрібен справжній OR.

16.8. Нуль проти неактивного входу

Відсутність фізичного сигналу не можна надійно перевірити функцією як відмінність від числового 0. Для запису стану окремо потрібні шина даних та Write. Reset подає явний нуль або DefaultArithmetic; закрита гілка сама по собі не означає запис 0.

16.9. Логічні тіки і межа scene

Усередині Circuit логічні тіки є стабільною моделлю часу. Однотикові події зберігаються при низькому FPS та зміні Circuit Speed.

Тест ланцюга із 1000 послідовних Diode показав рівно 1000 логічних тіків затримки. Тому внутрішні worker можуть використовувати фіксовані Delay, розраховані за критичним шляхом.

Цю детермінованість не можна автоматично переносити на однотикові взаємодії зі сценою, моторами, сенсорами та іншими world-level об'єктами.

16.10. Editor/cache і обов'язкова перекомпіляція перед тестом

Після редагування вкладеного Circuit редактор іноді показував старий результат або зберігав уже запущений startup-state instance. Перед тестом зміненої логіки потрібно оновити/перекомпілювати сам змінений Circuit і схеми, що його використовують, аж до кореневого виклику; це практичне правило розробки, а не властивість арифметичної моделі. Для чистого інтеграційного старту виконати project Run → Stop → новий Run. Якщо перевіряється зміна InitValue/InitBus, може знадобитися створення нового екземпляра пам'яті або повний restart симуляції.

Порядок діагностики: (1) перевірити актуальність вкладених та батьківських Circuit; (2) перезапустити проєкт; (3) повторити той самий тест; (4) лише якщо збій відтворився — міняти логіку. Інакше легко «лагодити» вже виправлену схему через застарілий кеш.

16.11. Розводка, Port та редактор

Public pin має напрямок за іменем, не за фізичним боком. Wire/junction/Via/Port лише маршрутизують лінії; великий M:MainController після cleanup використовує прямі магістралі та компактні внутрішні шини, без зайвих Port. В інших схемах Port може полегшити довгі переходи. Для перейменування однакових Port у редакторі раніше застосовували Rename (R) — це варто перевіряти разом із залежними public pin. Нормативне іменування — C§1, фактичний fan-out — M:MainController. 
При неочікуваних результатах інтеграції потрібно перевіряти не лише логіку, а й точний збіг назв внутрішніх Port та публічних пінів. Невідповідність Fits і -out-fits уже призводила до помилкового переходу в ERROR при правильному обчисленні.


-------------------------------------- 17. Повний dataflow і відновлення --------------------------------------

17.1. Прохід однієї команди

1) Кнопка → M:CommandEncoder: Command B2 + Capture.
2) M:InputController.SyncBuffer: один стабільний B2, RootValid.
3) M:StateController → M:FlowController: ModeCurrent + Code → затриманий Frozen Flow.
4) M:PreparationController: PRE/reset до PreReady.
5) MainValid → один із M:EntryController, M:CalculationController, M:MemoryController.
6) Worker: обчислення Candidate, завершення Compute, Work↓, copy до Current, Commit, WorkerRelease.
7) M:StateController: POST-check error/Fits, TargetMode, ModeCandidate/Current commit.
8) GlobalRelease: звільнити Command і Frozen Flow, скинути утримані release/error до наступної транзакції.

Рендеринг паралельний: EntryCurrent/ArithmeticCurrent/MCurrent → M:EntryRenderer або M:ResultNumberSelector → M:ResultRenderer; M:ErrorRenderer → M:DisplayController → M:Digit. Для ERROR або RESULT без Fits показується готовий Error Frame. Розводка всіх входів/виходів — M:MainController; формальна послідовність — C§35.

17.2. Три перевірки сценаріїв

- Цифра після RESULT: Flow 502; PRE очищує Entry, EntryController записує новий буквальний стан, POST встановлює ENTRY. Старий Result не перетворюється на нову цифру.
- Operation/Equals: Flow 503 у ENTRY, worker зчитує EntryNumber і за OpPending вирішує, чи застосовувати стару Operation; Equals завершує pending, зберігає Operand для повтору. C§23–24.
- MR при pending: CalculationController записує M у Operand і RhsReady=1; ResultNumberSelector показує Operand; M не змінюється. Наступний Equals/Operation вирішує арифметику. C§25, C§27.

17.3. Як відтворювати проєкт

Перш ніж будувати вузли, прочитати D§0.3 і C§1: B означає Bus, Number B4 не є одним native number, а публічні назви портів повинні точно збігатися. Послідовність складання залежностей, а не хронологія колишньої розробки:
1) Побудувати F-функції, M:Digit/Indicator, M:Memory/InitMemory/BusMemory/InitBusMemory, M:BusGate/Diode за точними реалізаціями F/M.
2) Зібрати M:SRFlag, M:ExecTimer, M:FeedbackSynchronizer, M:SyncBuffer; перевірити фронт/утримування, settle, rearm, Delay≥5.
3) Зібрати M:EntryState, M:CalculatorState та стартові значення; перевірити незалежність Current від Candidate при Work=1, запис нуля і commit.
4) Зібрати input/flow/preparation та робочі контролери; звірити ownership, Flow, sticky errors і час Compute/Commit із C§18–22, C§29–36, C§43.
5) Зібрати renderers, selector, DisplayController, потім M:MainController та фізичну scene. Перевірити порт за портом M:MainController, а не на око за розташуванням дротів.
6) Після правок перекомпілювати змінені та всі залежні схеми, очистити стан через Run → Stop → Run (D§16.10). Запустити інтегровані сценарії: startup, Entry/Backspace/Dot/sign, chaining, implicit/repeated Equals, M+/M−/MR/MC, Clear, overflow/div-by-zero, Fits, швидке/утримуване натискання, невідомий Mode. Результати не позначати PASS без фактичної перевірки.

17.4. Головні правила безпечної зміни

Не підміняти Candidate прямим Current feedback; не запускати наступну команду до GlobalRelease; не скорочувати Commit до ComputeDone; не передавати raw ALU error замість sticky; не з'єднувати активні числові джерела замість явного OR; не змінювати Number rounding заради дисплея; не переносити старі коди, старі startup-механізми та порти з архівної документації.

Порядок перевірки зміни: точна схема M/F → відповідний контракт C§ → залежні виклики в M:MainController → пояснення в цьому docs. Так комплект залишається придатним для повторного відновлення.
